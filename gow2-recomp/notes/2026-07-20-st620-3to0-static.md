## TL;DR — veredito

1. **A premissa "o handler do estado 3 encaminha `+0x744==1` para idle(0) em vez de 5" está
   REFUTADA.** O handler do estado 3 é `func_002C05F8` (`ppu_recomp_001.cpp:36595`); com
   `obj+0x744 != 0` ele escreve `st620=4` depois `5` e avança — **nunca escreve 0**.
2. **`st620=0` só é escrito pelo MovieStop `func_002BFF88` (`ppu_recomp_001.cpp:36141`)** e
   seus ramos de teardown (`func_002C0048`/`func_002BFFF4`/`func_002BFFE0`). Nenhum handler
   da FSM escreve 0. Logo **`3→0` é um Stop externo do movie, não uma decisão do estado 3.**
3. **O gate honesto de avanço do estado 3 é `func_0045B2A8(obj+0x720)`** — exactamente o
   `[MOVIEEOS] func_0045B2A8 -> 1 (state-3 gate)` do Windows. Ele devolve
   `*(resolve(obj+0x720)+0x1B8)` (estado da sessão de decode). No macOS `obj+0x720` **não tem
   sessão viva** (Task 2 provou `cellVdecOpen/StartSeq/DecodeAu = 0` na intro), então o gate
   devolve 0/-1, a FSM fica parada em 3, e o MovieStop leva a 0. **Essa é a precondição em
   falta — e não é `+0x744`.**
4. **`obj+0x744` é lido SÓ pela própria FSM** (9 leitores, todos em
   `func_002C0508/05F8/069C/0788/07D8/07F8` + espelhos — confirmado por EA de guest). A
   afirmação do commit `8bd5700` de que `func_000C3644` (chunk 004) é o "primeiro leitor
   não-FSM do `+0x744`" é **artefacto de return-address**: `func_000C3644`
   (`ppu_recomp_004.cpp:156798`) faz aritmética float e **não lê `obj+0x744`** (o único
   `0x744` do chunk 004 é `vm_write32(gpr[1]+0x744,…)`, escrita na *stack*).

## 2. Ponto de decisão 5-vs-0 do estado 3 — `func_002C05F8` (`ppu_recomp_001.cpp:36595`)

```
36596:  gpr0 = vm_read8(obj+0x744)                 // byte EOS f744
36597-98: if (f744 == 0) -> func_002C0688          // <ramo park>
36599:  st620 = 4                                    // (f744 != 0)
36601:  st620 = 5
36603:  -> func_002C060C                             // func_002C060C: st620=5 -> loc_002C0614
```

Decisão em guest: `vm_read8(obj+0x744)`. **`f744 != 0` → `st620=5` (avança).**
**`f744 == 0` → `func_002C0688` (cadeia de park).** Não existe aqui rota para 0 com `f744==1`.
(Mesmo corpo inline em `func_002C05C8`@`ppu_recomp_002.cpp:224755-224761`, em
`func_002C0570`@`:224703-224709`, e no inline do pump `_001:36550-36556`.)

### Cadeia de park (f744==0) — onde 5-vs-"fica em 3" se decide de verdade

- `func_002C0688` (`ppu_recomp_002.cpp:224835`): lê **`obj+0x746`**; `!=0` → `st620=4`
  (avança via `func_002C0694`); `==0` → `func_002C0FA0`.
- `func_002C0FA0` (`ppu_recomp_002.cpp:224850`, decisão `:224853-224856`):
  ```

  ```

Portanto o avanço "não-forjado" do estado 3 depende de **`func_0045B2A8(obj+0x720) != 0`**.

## 3. Quem escreve `st620=0`: só o MovieStop (não a FSM)

`func_002BFF88` (`ppu_recomp_001.cpp:36141`) = **MovieStop/Close** (mesmo `obj` do pump):
lê `st620`; se `st620==0` → `func_002C0048`; se `st620==0xB` → `func_002C008C`; **se
`1..10` (estado 3 incluído) → liberta `obj+0x720/0x724/0x728/0x72C` e escreve `st620=0`**.

Escritores de `st620=0` (todos ramos do MovieStop):
- `func_002C0048` — `st620=0` em `ppu_recomp_002.cpp:224657` (/ `_001:36203`).
- `func_002BFFF4` — `st620=0` em `ppu_recomp_002.cpp:224637`; **também zera `obj+0x720`**
  (via `func_00445C48`) — destrói o próprio handle que o gate precisa.
- ramo `func_002BFFE0` — `st620=0` em `ppu_recomp_002.cpp:224594`.

Os handlers da FSM só escrevem `st620 ∈ {2..0xB}`; `st620=1` vem do Play/init
(`_001:36468`). **Nenhum handler escreve 0.** Logo `3→0` = MovieStop.

Chamadores do MovieStop (`func_002BFF88`): `_005:55075` (loop do estado 11, em
`loc_002C0D50` após condições de fim), `_005:55258`, `_001:37136`, e **`_000:8019` dentro de
`func_00018030`** — gestor de nível alto que chama Stop quando `func_002BFA48()==0`,
**independente do estado da FSM**. Ou seja, o movie pode ser parado com `st620==3` por código
acima da FSM → `3→0`.

## 4. O gate `func_0045B2A8` = o "state-3 gate" do Windows

`func_0045B2A8` (`ppu_recomp_001.cpp:425951`):
```
r = func_004479E8(handle)              // handle = obj+0x720
return (r == 0) ? -1 : *(r + 0x1B8)    // estado da sessão de decode
```
`func_004479E8` (`ppu_recomp_001.cpp:407271`) é um resolver de handle geracional (tabela em
`TOC-0x394`, stride `0x1E4`, valida geração/índice; devolve 0 para handle nulo/stale/fora de
range). Portanto:

**Precondição honesta de `3→5` = `obj+0x720` guarda um handle de sessão vivo cujo
`*(sessão+0x1B8) != 0`.** No Windows o SEQDONE do decode põe esse campo → `func_0045B2A8 -> 1`
→ estado 3 avança → WADs abrem. No macOS não há sessão em `obj+0x720` (Task 2:
`cellVdecOpen/StartSeq/DecodeAu = 0` na intro) → `func_0045B2A8` devolve 0/-1 → fica em 3 →
MovieStop → `3→0`.

## 5. `obj+0x744` é lido só pela FSM (refutação do "consumer" externo)

`grep` por EA de guest — 9 leitores de `vm_read8(...+0x744)`, **todos** na FSM do movie:
`func_002C0508`(`_001:36550`), `func_002C05F8`(`:36596`), `func_002C069C`(`:36652`),
`func_002C0788`(`:36736`), `func_002C07D8`(`:36761`), `func_002C07F8`(`:36792`);
espelhos `func_002C0570`(`_002:224703`), `func_002C05C8`(`_002:224755`),
`func_002C0804`(`_005:54731`). **Zero leitores fora da FSM.**

O read-hook (`ps3recomp/runtime/ppu/ppu_loader.cpp:723-726`) é override cego do EA inteiro:
`if (g_movie_eos_ea && a==g_movie_eos_ea) return 1;` — devolve 1 a **qualquer** leitor de
`obj+0x744`. Como todos os leitores são a FSM, o único efeito honesto do arme é: quando o
pump reentra no estado 3, `func_002C05F8` lê 1 e avança para 5. O commit `8bd5700` atribuiu o
"primeiro leitor" a `func_000C3644` por `ra` do host — mas `func_000C3644`
(`ppu_recomp_004.cpp:156798`) faz mul/add de float e **não lê `obj+0x744`**; é artefacto de
return-address (PIE+trampolim). A observação empírica válida desse commit ("`st620` sai de 3
antes de `func_002C05F8` reentrar") é consistente com **o MovieStop ganhar a corrida**, não
com um consumidor de `+0x744`.

## Respostas aos 3 pontos do deliverable

**(1) file:line onde o estado 3 decide 5-vs-0 + condição.**
Handler do estado 3 = `func_002C05F8` @ **`ppu_recomp_001.cpp:36595`** (decisão `:36596-36603`):
`vm_read8(obj+0x744)`; `!=0 → st620=5`; `==0 → func_002C0688`. **Não há rota para 0 com
`+0x744!=0`.** A decisão real "avança-vs-fica-em-3" (quando `+0x744==0`) é
`func_002C0FA0` @ **`ppu_recomp_002.cpp:224850`** (`:224853-224856`):
`func_0045B2A8(obj+0x720)!=0 → avança`; `==0 → fica`. A escrita de `st620=0` é
**`ppu_recomp_002.cpp:224637`/`:224657`/`:224594`** (MovieStop `func_002BFF88` @
`ppu_recomp_001.cpp:36141`).

**(2) `func_0045B2A8` é a precondição em falta, ou `3→0` é intencional / WAD noutro sítio?**
`func_0045B2A8(obj+0x720)` **é** o segundo gate (o "state-3 gate" do Windows) e a sua
precondição — sessão de decode viva em `obj+0x720` com `*(sessão+0x1B8)!=0` — **não está
satisfeita** no macOS (sem `cellVdec` aberto na intro; Task 2). `3→0` **não** é decisão do
handler do estado 3: é o **MovieStop** (`func_002BFF88`, único escritor de `st620=0`),
chamável pelo gestor de nível alto (`func_00018030`@`_000:8019`) em qualquer estado 1..10.
Consequência: forjar `+0x744` foi sempre a alavanca errada — mesmo que `func_002C05F8` avance
para 5, os estados a jusante (4/5/10) e o gate lêem a mesma sessão vazia (`obj+0x720`,
`obj+0x714`, `obj+0x724`), e o MovieStop leva a 0. **O flag em falta é o estado da sessão de
decode `*(resolve(obj+0x720)+0x1B8)`, que o SEQDONE põe no Windows.**

**(3) Próxima experiência única (diagnóstico, NÃO implementar).**
Instrumentar (só leitura, env-gated) **`func_0045B2A8` @ `ppu_recomp_001.cpp:425951`**:
logar o handle de entrada (`obj+0x720`) e o valor devolvido (`*(sessão+0x1B8)` ou -1) por
chamada; **e** um trap de leitura no **MovieStop `func_002BFF88` @ `ppu_recomp_001.cpp:36141`**
logando `st620`-no-Stop. Correr o recipe NATURAL. Discriminador:
- Se `func_0045B2A8` nunca vê handle válido (`obj+0x720==0` → resolver devolve 0 → gate -1),
  a sessão de decode nunca existiu → o fix pertence ao canal FORCE/vdec (pôr uma sessão
  real/HLE em `obj+0x720` para `+0x1B8` virar), **não** ao `+0x744`.
- Se o MovieStop dispara com `st620==3` logo após o arme, confirma-se que o Stop ganha a
  corrida ao avanço — `+0x744` é ortogonal ao desbloqueio dos WADs.
Ambos observam o flag de guest que o caminho-WAD realmente exige (`obj+0x720`/`+0x1B8`) sem
escrever estado nenhum.
