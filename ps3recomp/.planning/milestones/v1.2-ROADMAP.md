## Phase Details

### Phase 12: Scaffold Go + elfinfo

**Goal:** A árvore Go existe, compila, e um comando `elfinfo` prova parity estrutural com `elf_parser.py` sem tocar no path de `boot_gow2`.  
**Depends on:** Nada técnico do v1.1 (só disciplina: não misturar commits de boot com commits Go se worktree partilhado).  
**Requirements:** GO-01, GO-02 (parcial), GO-03 (stub), GO-05, GO-10  

**Success Criteria:**

1. `cd tools/go && go test ./... && go build -o bin/elfinfo ./cmd/elfinfo` (ou layout equivalente) passa em arm64 macOS.
2. Corrido no EBOOT local: JSON de entry/machine/phnum e contagem de imports **bate** com `python tools/elf_parser.py … --json` nos campos documentados (diff script).
3. Nenhum script de build do GoW2 chama o binário Go por default (GO-10).
4. `docs/TOOLS_GO.md` existe com “como buildar” e “Python ainda canónico”.

**Plans:** (a criar com `/gsd-plan-phase 12` quando o marco for activado)

Sugestão de planos:

- 12-01: `go.mod` + layout `cmd/elfinfo` + `internal/elf`
- 12-02: parity script vs `elf_parser.py` + fixture mínima sem ELF de jogo no git
- 12-03: doc TOOLS_GO + .gitignore de `bin/`

---

### Phase 13: ppu-disasm Go + corpus parity

**Goal:** O decoder PPU em Go é fiável o suficiente para ser base de lift; regressões de opcode são apanhadas por teste.  
**Depends on:** Phase 12  
**Requirements:** GO-02, GO-04, GO-06, GO-11  

**Success Criteria:**

1. `go test` cobre famílias críticas (integer, branch, load/store, VMX sample, RLD, invalid skip).
2. Corpus gerado **localmente** a partir do EBOOT (não commitado): parity ≥99,9% vs `ppu_disasm.py`; relatório de misses.
3. `parity_gate.sh` (ou target make) falha se limiar quebrar (GO-11).
4. CLI `ppu-disasm` documentada com flags espelhando o essencial do Python.

**Plans (sugeridos):**

- 13-01: port tabelas/decode core + testes unitários
- 13-02: harness parity corpus + gate
- 13-03: bugs de parity encontrados → fix + casos de teste

---

### Phase 14: find-functions + ppu-lift PoC

**Goal:** Provar que bounds + emissão C em Go batem no Python num golden set pequeno mas representativo — sem pretender 52k funções.  
**Depends on:** Phase 13  
**Requirements:** GO-07, GO-08, GO-09  

**Success Criteria:**

1. `find-functions` recall ≥95% vs `functions.json` (ou baseline documentado) no EBOOT local; misses em JSON.
2. `ppu-lift` emite C para N≥20 funções golden; aceite GO-08 (compile harness e/ou diff normalizado).
3. Benchmark Python vs Go no golden set escrito em results (GO-09).
4. Ainda opt-in; smoke intro **não** é aceite desta fase (só “não regredir se ninguém activar Go”).

**Plans (sugeridos):**

- 14-01: OPD seed + prologue/epilogue bounds
- 14-02: emitter mínimo (subset opcodes do golden)
- 14-03: golden set + parity/lift tests + bench

---

### Phase 15: Integração opt-in + veredicto

**Goal:** Decisão de produto documentada com números; se PROMOTE, roadmap v1.3 esboçado; se HOLD, custo afundado limitado ao PoC.  
**Depends on:** Phase 14  
**Requirements:** GO-03 (completo), GO-10, GO-11, GO-12  

**Success Criteria:**

1. Flag opt-in documentada (`PS3_LIFT_ENGINE=go` ou `ppu-lift` path) — default Python.
2. `verify`-style: parity_gate no CI **só** se `tools/go` existir e job for non-blocking ou path separado (não partir CI do runtime).
3. `.planning/milestones/v1.2-VERDICT.md` com PROMOTE | HOLD | HYBRID + tabela de métricas.
4. Se HOLD: Python permanece único path; código Go pode ficar como experiment.
5. Se PROMOTE/HYBRID: lista de fases v1.3 (SPU, full lift, midasm port) **sem** implementar ainda.

**Plans (sugeridos):**

- 15-01: wire opt-in + doc final
- 15-02: CI job informativo
- 15-03: VERDICT + MILESTONE audit stub
