## Tech Debt

**Single giant lock serializes all PPU guest execution — [documented]+[verified]:**
- Issue: every lifted PPU function and HLE handler assumes single-threaded guest execution; none of the shared runtime state (C heap, HLE dispatch tables, `s_lwmutex[]`/`s_lwcond[]` slot arrays) is protected against concurrent host threads. The interim fix is one process-wide lock around all guest code, same pattern as CPython's GIL.
- Files: `runtime/ppu/ppu_loader.cpp:41-56` (design comment), Windows `SRWLOCK` impl `runtime/ppu/ppu_loader.cpp:57-106`, POSIX/macOS `pthread_mutex_t g_ppu_giant_lock` impl `runtime/ppu/ppu_loader.cpp:209-291`. Same pattern echoed in `runtime/syscalls/sys_event.c`, `runtime/syscalls/sys_timer.c`, `runtime/syscalls/sys_ppu_thread.c`, `runtime/syscalls/sys_semaphore.c`, `libs/video/cellGcmSys.c`, `libs/video/rsx_commands.c`, `libs/codec/cellVdec.c`, `libs/codec/cellAdec.c`, `libs/system/sysPrxForUser.c`, `libs/spurs/cellSpurs.c`.
- Impact: every real blocking point (`sys_timer_usleep`, `sys_lwcond_wait`, …) must remember to release the lock before blocking and reacquire after; a missed release/reacquire stalls every other PPU thread. This is a correctness-by-discipline invariant, not enforced by the type system — a new HLE handler that blocks without releasing the lock silently deadlocks the whole guest.
- Fix approach: audit every blocking syscall handler for release/reacquire pairing (there is no compile-time check); longer-term, move to fine-grained locking per shared structure once the SPURS/thread model stabilizes. CLAUDE.md explicitly frames this as an "as an interim measure."

**PPU lifter fallthrough cross-fragment bug class — [documented]+[verified, tooling exists]:**
- Issue: `tools/ppu_lifter.py` auto-appends `g_trampoline_fn = func_XXXXXXXX; return;` whenever a lifted function's last instruction is not a terminator, targeting the function's recorded `end` boundary. If `tools/find_functions.py`'s heuristics mis-detect a function boundary mid-body (a coincidental `mflr r0` bit pattern misread as a new prologue), the recorded `end` is drawn too early and the auto-appended fallthrough trampolines into a phantom neighbour instead of the true continuation — the root cause behind the historical `func_002550C8` bug (fixed via `games/gow2/recomp_mid_v2/patch_fallthrough_2550c8.py` — the *patch script* is tracked in this repo; it is the `ppu_recomp_*.cpp` output it rewrites that is gitignored).
- Files: pattern documented and now covered by an actual auditor tool, `tools/audit_fallthrough.py` (long design comment at `tools/audit_fallthrough.py:1-80` walking through the detection signature — target IS the recorded `end` boundary, a registered adjacent function, sitting close to a suspiciously small fragment). Companion test suite `tools/test_audit_fallthrough.py`. Emission sites in the lifter: `tools/ppu_lifter.py:1432`, `:1444`, `:1511`, `:1524`, `:3231`.
- Impact: a silent mis-lift produces code that *compiles and runs* but jumps to the wrong function on fallthrough, corrupting control flow in a way that is very hard to spot without exactly this kind of static audit — it looks like ordinary tail-call-shaped code.
- Fix approach: the auditor exists, has a documented detection algorithm, and its **unit tests do run in CI** (`tools/test_audit_fallthrough.py` is listed in `scripts/test_python.sh:103`, invoked by all three CI jobs). What is *not* wired anywhere — **[verified]** by inspecting `.github/workflows/ci.yml` and `scripts/test_python.sh` — is any invocation of the auditor against **real lift output**: CI proves the auditor's own logic works, never that the shipped GoW2 lift is clean. Recommend running `tools/audit_fallthrough.py --cpp <generated .cpp>` against the live GoW2 lift before the next re-lift, and wiring it into the pre-relift checklist. (CI cannot do this itself: the generated `.cpp` is gitignored game-derived output and never present in a clean checkout.)

**Fixes to gitignored generated lift output only survive as external patch scripts — [documented]+[verified]:**
- Issue: `ppu_recomp_XXX.cpp` files under `games/gow2/recomp_mid_v2/` are gitignored (regenerated by the lifter) and edited directly for probes/fixes during debugging sessions. Each fix is supposed to be re-encoded as an idempotent `patch_*.py` script so it survives a re-lift.
- Files: **73** `patch_*.py` scripts, all under `games/gow2/recomp_mid_v2/` and all tracked in git (e.g. `patch_fallthrough_2550c8.py`, `patch_freelist_guard_262610.py`, `patch_shadersrc_loop.py`, `patch_type15_cb56c_highbit.py`). Verified with `find . -name 'patch_*.py'` (73, single directory) cross-checked against `git ls-files 'games/gow2/recomp_mid_v2/patch_*.py'` (73 — none gitignored).
- Impact: a re-lift that runs the lifter but skips re-running these scripts silently regresses every one of those fixes with no compiler error and no obvious symptom until the specific code path is exercised again. There is no single driver script found in this sweep that runs all `patch_*.py` in sequence after a re-lift — each session must remember which ones apply and in what order.
- Fix approach: **[suspected]** — a single `apply_all_patches.py`/Makefile target that runs every `patch_*.py` against a fresh lift output in a known order, plus a checksum/manifest of which source functions each patch touches, would remove the "did we forget one" risk. Not found to exist currently; worth confirming with the owner before building it (may already live in `../gow2-recomp`, the sibling repo, which was out of scope for this sweep of `ps3recomp` itself).

**SPURS LFQueue ANY2ANY direction unimplemented — [verified]:**
- Symptoms: `_cellSpursLFQueuePopBody` returns `LFQ_ERR_AGAIN` unconditionally for any lock-free queue configured with `DIR_ANY2ANY`, logging `"PopBody on ANY2ANY queue 0x%X: v2 protocol not implemented"`.
- Files: `libs/spurs/cellSpursLFQueue.c:569-584`.
- Trigger: any guest code (SPURS job or PPU-side) that pops from an ANY2ANY-direction lock-free queue.
- Workaround: none — callers must avoid ANY2ANY queues or treat every pop as a busy-retry against `LFQ_ERR_AGAIN`. Confirmed in CLAUDE.md's own follow-up list as one of several "bloqueadores de promoção spu2/3 a default" items still open.

## Security Considerations (memory safety / untrusted guest input)

**Guest memory access is centrally bounds-checked — [verified, positive finding]:**
- All guest loads/stores go through `vm_read8/16/32/64/_f32/_f64` and `vm_write*` in `runtime/ppu/ppu_memory.h:60-153`, every one of which calls `ppu_guest_range_committed(addr, n)` first and returns a safe default (0 / 0.0f) rather than dereferencing on a miss. This guards against garbage guest addresses (uninitialized handles, failed allocations used as pointers) causing a genuine host access violation — explicitly the motivation documented at `runtime/ppu/ppu_memory.h:33-42`.
- This is a strong baseline, but it depends on every callsite going through these helpers rather than raw `vm_ptr8`/`vm_translate` + direct dereference. `vm_ptr8/16/32/64` (`runtime/ppu/ppu_memory.h:52-55`) perform NO bounds check themselves — they are raw pointer arithmetic. **[suspected]** — a grep-based audit of direct `vm_ptr32(...)`/`vm_translate(...)` dereferences outside the `vm_read`/`vm_write` wrappers (e.g. in lifted `.cpp` code or HLE handlers that need a raw pointer for `memcpy`) was not exhaustively completed in this sweep; worth a dedicated pass since any such site bypasses the range check.

**RSX texture decode paths bound guest reads via an explicit span calculator before touching guest memory — [verified, positive finding]:**
- `libs/video/rsx_live_draw.c:628-637` computes the full mip-chain byte span from guest-controlled width/height/format before calling `guest_ptr(location, offset, span)`, which itself is a thin wrapper (`rsx_live_draw.c:187-191`) delegating to a host-supplied bounds-checking callback (`g.guest_ptr`) that returns `NULL` on failure — checked at `rsx_live_draw.c:602` and `:637` before any read. Host-side scratch allocations (`rsx_live_draw.c:643 malloc((size_t)mw * mh * 4)`) are null-checked (`oom` flag, `rsx_live_draw.c:644`) and freed on every exit path (`rsx_live_draw.c:661`).
- No denial-of-service ceiling on `w`/`h` themselves was found before the span/malloc computation — a guest RSX texture register with an implausibly large width/height (e.g. via a corrupted or malicious WAD) could request a very large host allocation. **[suspected]** — this is a DoS/OOM risk, not a memory-corruption risk (malloc failure is checked), and PS3 RSX texture dimensions are hardware-limited in practice by the real console's register field widths, which likely caps this in normal operation; whether the recompiler enforces the same field-width limit on the guest-supplied value was not confirmed in this sweep.

**Offline ELF/WAD parsing tools operate on untrusted lifter-input binaries without a hardened error path — [suspected]:**
- `tools/elf_parser.py` (897 lines) does raw `struct.unpack_from` reads driven by header-declared offsets/counts (`tools/elf_parser.py:116-128`) against `self.raw_data = f.read()` (`tools/elf_parser.py:644`) with no exception handling visible around the unpack calls in the sampled region. A malformed ELF/SELF (e.g. a corrupted or deliberately crafted EBOOT) can cause an unhandled Python exception (index/struct.error) — a hard crash of the offline lifting tool, not a runtime memory-safety issue, since this code never ships in `boot_gow2`/`boot_v2_new.exe`. Low severity given it's a developer-only pipeline tool, but worth a `try/except` wrapper with a clear error message before feeding third-party or fan-provided game data through the pipeline.

## Fragile Areas

**`libs/video/cellGcmSys.c` (2000 lines) mixes production RSX FIFO processing with multiple env-gated diagnostic/demo paths inline — [verified]:**
- Files: `libs/video/cellGcmSys.c` — FIFO drain loop, draw-path method tracing (`PS3_RSX_STATS`, `PS3_RSX_DUMP`, `:613-635`, `:679-697`), and the `PS3_SHADER_DEMO` injection (`:639-667`) all live in the same function bodies as the real command processing.
- Why fragile: the diagnostic code paths are toggled by 5+ different env vars checked with `static int` caching idioms repeated at each callsite (`if (x < 0) { x = getenv(...) ? 1 : 0; }`), making it easy to introduce a state bug (e.g. wrong static var reused, gate check moved after a side effect) when adding a new probe.
- Safe modification: keep new diagnostics in separate helper functions taking the current RSX state as a parameter, called from one line in the hot path, rather than inlining new gated blocks directly into the FIFO loop body.
- Test coverage: `libs/video/tests/` has RSX trace and replay tests (`libs/video/tests/test_rsx_trace.c`, `replay_main.c`) but coverage of the specific env-var-gated demo/dump paths was not confirmed.

**`tools/ppu_lifter.py` (4315 lines, the largest file in the repo) is the sole source of both correctness-critical control-flow codegen and the historical fallthrough bug class — [verified]:**
- Files: `tools/ppu_lifter.py`.
- Why fragile: single very large module responsible for boundary detection interplay (via `tools/find_functions.py`), trampoline emission (`:1432-3231`), and the emission logic the fallthrough auditor (`tools/audit_fallthrough.py`) exists specifically to check after the fact. A change to trampoline emission logic risks reintroducing the same class of bug in a new shape not yet covered by the auditor's detection signature (which is deliberately narrow — "target IS the recorded `end` boundary" — per `tools/audit_fallthrough.py:35-38`).
- Safe modification: any change to fallthrough/trampoline emission in `ppu_lifter.py` should be paired with running `audit_fallthrough.py` against a fresh lift of at least the GoW2 EBOOT before merging, plus the existing `tools/test_audit_fallthrough.py` / `tools/test_ppu_lift.py` suites.
- Test coverage: `tools/test_ppu_lift.py` (1082 lines) and `tools/test_audit_fallthrough.py` are substantial and **both run in CI** — listed in `scripts/test_python.sh:103-107`, executed by the `macos`/`linux`/`windows` jobs of `.github/workflows/ci.yml` on every push and PR. **[verified]** — this is a strength, not a gap. The residual gap is narrower: these suites exercise the lifter against synthetic fixtures only, never against a real game lift (see the fallthrough entry above).

**Upstream merge history is high-risk by the project's own account — [documented]:**
- Files at risk on any `upstream/master` merge (per CLAUDE.md, verified as existing files): `runtime/ppu/ppu_loader.cpp` (sticky FIOS, giant lock, `g_movie_eos_ea`, PS3_PERF, store-preempt soft), `libs/system/sysPrxForUser.c` (lwcond gen / lazy mutex EA / FIOS sched).
- Why fragile: CLAUDE.md documents that the v0.7 "First Draw" merge already broke the intro boot smoke test once (`st620` regressed to 0, OOB stack), requiring either `--ours` conflict resolution on the two files above or a full revert + ordered cherry-pick. Recorded macOS portability landmines specifically bitten before: Win32 APIs leaking into POSIX code, `<intrin.h>` on Apple, `st_atim` vs `st_atimespec`, and new lifter-emitted symbols (`ppu_guest_call`, `g_last_hle_*`, `spurs_task_kick_all`, etc.) needing stubs because CMake excludes `runtime/ppu/` from the static lib on macOS (`boot_*` links those objects separately).
- Safe modification: follow the documented merge receipe in CLAUDE.md exactly (map divergence with `comm`, per-file `--ours`/`--theirs` policy, mandatory post-merge macOS portability checklist, mandatory 25s non-regression smoke before committing). No evidence in this sweep that this checklist is automated (e.g. as a script) — it is currently a manually-followed markdown recipe, which is itself a process-fragility risk (a rushed merge session can skip a step).

## Performance Bottlenecks

**Giant lock forces fully serialized guest execution — [documented, already covered under Tech Debt]:**
- No independent evidence of a specific measured slowdown was found in this sweep (no profiling output committed to the repo); flagged here only as the structural ceiling this project has already identified — every additional real worker thread the game spins up adds contention on one process-wide lock rather than gaining parallelism.

**RSX texture decode does a scalar per-texel software decode/deswizzle loop on the CPU — [verified]:**
- Files: `libs/video/rsx_live_draw.c:641-659` — nested `for (y) for (x)` loop calling `decode_texel(...)` per texel with a `morton_index` computation per texel for swizzled (non-linear) textures (`rsx_live_draw.c:472` morton_index, `:651` per-texel call site).
- Impact: this runs on every texture bind that isn't already cached (`rsx_live_draw.c:567-579` texture cache lookup gates it), so steady-state cost after warm-up should be low; a cold scene with many uncached textures will pay a scalar decode cost per texel with no SIMD path visible in the sampled region. **[suspected]** — not confirmed to be an actual measured bottleneck; flagged as a candidate given the project's stated pixels-in-frame goal will increase texture volume.

## Scaling Limits

**Boot logo queue fixed at 6 entries — [verified]:**
- Files: `libs/video/rsx_host_content.c:26` `#define BOOT_LOGO_MAX 6`, enforced at `rsx_host_content.c:109-114` (drops and logs on overflow rather than growing).
- Current capacity: 6 queued boot logos (host-side RGBA copies).
- Limit: a 7th `rsx_host_boot_logo_push` call is silently dropped with a stderr log; not a crash, but content past the 6th queued logo is lost.
- Scaling path: trivial — raise `BOOT_LOGO_MAX` or switch to a dynamic array; low priority since this gates a small, game-specific fixed sequence (boot/legal/studio logos), not per-frame content.

## Dependencies at Risk

**Fork carries permanent divergence from `sp00nznet/ps3recomp` upstream — [documented]:**
- Risk: this repo is a long-lived fork with macOS-specific and GoW2-specific code that must never be blindly overwritten by upstream merges (see Fragile Areas above). Every upstream sync is a manual, checklist-driven, historically break-prone operation.
- Impact: correctness fixes landing in upstream (PPU lifter callee-save handling, jump tables, `lmw`/`stmw`, VMX big-endian handling, SPU `brsl`, lv2 syscall renumbering) are not automatically available here and must be cherry-picked with care; conversely this fork can silently fall behind on genuine bug fixes if merges are deferred too long out of merge-risk aversion.
- Migration plan: none needed (intentional fork architecture) — the documented mitigation is the ordered cherry-pick fallback (lifter → SPU lifter → syscalls-with-smoke → GCM/RSX) described in CLAUDE.md when a full merge regresses the boot smoke.

## Test Coverage Gaps

**CI exists and is broad, but stops at the engine boundary — no automated gate covers a real game lift or the boot path — [verified]:**
- What IS automated: `.github/workflows/ci.yml` runs on every push, PR and `workflow_dispatch`, with three jobs — `macos-latest`, `ubuntu-latest`, `windows-latest`. Each installs Python >=3.11 and runs `scripts/test_python.sh` (6 self-test suites incl. `tools/test_audit_fallthrough.py`, `tools/test_ppu_lift.py`, `tools/test_recomp_config.py`, `runtime/ppu/tests/test_ppu_lifter_emit.py`) then `scripts/test_runtime.sh` (cmake configure + build + ctest). Cross-platform build regressions and the macOS portability landmines listed above are therefore caught automatically.
- What's NOT tested by automation: (a) any lift of a real title — the GoW2 `EBOOT.ELF` and the generated `ppu_recomp_*.cpp` are game-derived and never present in a clean checkout, so no CI job can exercise them; (b) the 73 `patch_*.py` fixups — nothing verifies they still apply cleanly to fresh lifter output; (c) the boot/intro smoke (`st620` progression, sticky publish), which remains a human-run ~25s window per CLAUDE.md; (d) the RSX/Metal/D3D12 draw path, which needs a GPU and real assets.
- Risk: the regressions that have actually hurt this project historically — a bad merge breaking the intro boot, a lifter change silently regressing a `patch_*.py` fix, a fallthrough mis-lift — all live squarely in the untested band (a)–(c). CI's green check is a genuine signal about the engine, and no signal at all about the port.
- Priority: Medium — closing (b) is the cheapest and highest-value: a driver that applies all 73 patches to a fresh lift and fails loudly on the first non-applying hunk would be runnable locally even though CI cannot host the inputs.
