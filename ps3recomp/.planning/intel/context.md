## Topic: SPU PPU-fallback registry
- source: docs/SPU_FALLBACK.md
- notes: ps3recomp does not execute SPU code in this model (no SPU ISA JIT, no SPU local-store model). For many games this is acceptable — SPU jobs often produce side effects nothing depends on, or the PPU is satisfied when the group reports all threads exited cleanly. Games that need real SPU output (PhyreEngine asset decompressors, audio mixers, particle simulations, physics) would otherwise read garbage. The registry lets a per-game shim provide a PPU-side implementation for any SPU job, keyed on the SPU image's entry point; when the game starts a thread group, threads with a matching fallback run the shim. Documents the API, lifecycle, execution model, local store handling and caveats.

## Topic: GoW2 primary asset pipeline (R_PermA) root-cause trace
- source: docs/gow2-asset-pipeline-map.md
- notes: Evidence-before-hypothesis trace of `R_PermA.wad_ps3` consumption (Plano 3, Task 2), sourced from a 32,317-line `PS3_TRACE_ASSET=1` log plus WAD inspection and lifted code. Key finding: `R_PermA.wad_ps3` is an **uncompressed** WAD (a directory of named asset groups — `GFXX_ TXRX_ MATX_ LGTX_ FLPX_ CXT_ ANMX_ SCRX_ BHVX_ MDLX_ PRTX_ CAMX_ EEPR_ SNDX_ COLX_ SHGX_ FX_ WYPX_ …` — plus raw payload) that does not pass through zlib/edgezlib, so `push2=0` and `HOSTINFL=0` are the **correct** behaviour and the "producer-consumer deadlock in dearchive/inflate" thesis is a red herring for `R_PermA`. The break it identifies: the guest free-list allocator `func_00263178` dereferences a word tagged `0x80000000` from the free list **as a raw pointer**, producing a burst of writes to an uncommitted arena around `~0x84000000` that the VM guard drops; the allocation fails or corrupts, the WAD loader cannot place the next asset group, and the stream stalls. Also documents the async read path: `op=0x008695D4` → `func_002B3D1C` reading immediately into a guest ring at `~0x40080000` (a ~147 KB wrapping window), setting `op+0x14=pos+n` and `op+0x8=0`, with `movie_io_pread` always completing from the host and the pump poll `func_002B45D0` reporting done immediately — explicitly not the bottleneck.
- caveat: the stall it measures (linear stream stopping at 5,619,712 of 20,169,344 bytes, 27.9%) has since been overtaken — later sources record `R_Perm` reaching the full 20,169,344 bytes, and the project's own history attributes the fix to a cross-fragment fallthrough bug in `func_002550C8`.
